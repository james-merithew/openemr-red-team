Threat model — the surface we attack

6 categories · mapped to OWASP web + LLM Top 10

The Co-Pilot already treats the LLM as an untrusted planner behind a two-layer authz gateway, a fail-closed verifier, and an always-on critic. The model maps the whole surface and marks honestly where that spine holds and where it is thin — so the platform spends its budget on real risk.

Tool misuse

A04LLM08Covered

Denial of service

Per-turn cost caps are strong; the in-memory, proxy-spoofable rate limiter (absent on unauth routes) is the weak layer.

A05LLM10Partial

Identity / role

Persona hijack neutralized by server-assigned roles; HMAC token, ACL-at-mint. Dev-mode is the deploy footgun.

A01A07Covered*

Prioritization

Coverage is weighted to the least-defended, highest-impact cells first: indirect injection (no content sanitization), info disclosure (/ready, /metrics), and DoS / rate-limit exhaustion. The hardest and best-defended surface — cross-patient escalation — runs continuously as invariant-holds regression proofs: the attack is expected to fail, and the case exists to catch a future regression.

05

What "fixed" actually means

the regression pass-semantics — the intellectual centerpiece

A regression test passes only when the safe invariant held — proven by a deterministic check and the independent Judge across the attack's mutation family — never because a specific payload string stopped working.

01 · veto
The deterministic check is a hard veto — if code says PHI leaked, the case fails regardless of the Judge.
02 · downgrade-only
The Judge can only downgrade a deterministic pass (catch a semantic obey), never upgrade a fail.
03 · mutation family
On re-run the Red Team re-applies mutations, so a behavior change that dodges the literal payload still fails.

The case schema enforces this structurally: a model_validator rejects any case that asserts no invariant — so a static payload list cannot even be authored. ✓ verified: the static-payload case is rejected at load.

07

Triage — 13 findings, honestly sorted

the Documentation agent's output, usable for real decisions

2 CRIT 3 HIGH 3 MED 5 FALSE-POSITIVE
CRIT dev-token exposure · indirect injection HIGH rate-limiter · unauth routes · /ready disclosure MED /metrics binding · dev key · map growth FALSE-POS SQLi · cross-patient · LLM writes · VLM · laundering

The false-positive cluster is the point: a naive scanner flags "no-pid tool lets cross-patient reads" or "the LLM writes to the DB" — each is actually mitigated by the deterministic spine (that missing pid is the guard; the agent tier is read-only). An autonomous agent that files confident false positives wastes engineering time; validating against the spine is what makes the output trustworthy.

08

AI-use disclosure & the drifting judge

every AI decision has a deterministic check or human gate downstream

Where AI acts — and what follows it

  • Red Team generation → Judge veto + contract validation
  • Judge verdict nuance → deterministic safety facts + order-swap consistency
  • Orchestrator mutation strategy → deterministic ranking + budget ceiling
  • Documentation prose → deterministic fact passthrough + human gate on critical

Detecting a drifting judge

A frozen golden verdict set — human-labeled attempts with known-correct verdicts — is re-run on every Judge deploy. Divergence from the frozen labels is a drift alarm: pin to last-known-good, human-review the divergences, re-label only by hand. The same "regenerate and compare against committed truth" discipline as the openapi.json drift guard.

The deterministic veto stays authoritative throughout — a drifted judge can degrade nuance but can never manufacture a false-safe verdict.
